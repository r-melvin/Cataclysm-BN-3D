03. The new UI: design

Scope: the whole player-facing interface of Cataclysm: Bright Nights 3D, with the 3D renderer as the primary presentation. The classic 2D tiles mode keeps its sidebar and gets every new screen unchanged. The curses build is retired (user decision 2026-10-21; see 06_frontend_options.md §4).

Nothing here changes a game rule. Where a rule change would simplify the UI it is listed under "Feature cuts (last resort)" with the alternatives that were rejected first.

Evidence references are to 01_pain_points.md (P1-P10), 02_patterns.md and the files in research/.

1. Principles

  1. One screen per job. Every piece of state and every verb has exactly one home. If two screens can do the same thing, one of them is deleted. (P1, P5, P8.)
  2. One interaction verb. Look at a thing, see the prompt, press the key. Dedicated verb keys (open, close, smash, pick up, examine, talk, board) become optional bindings, not the way in. (P1: "throw the entire list at you every time"; P8.)
  3. The world shows, the text tells. In-world presentation (sky, weather, badges, arrows, combat text) may replace sidebar text, but every item of state stays available as text on demand: the F4 status report, the character screen, the log. No state is image-only.
  4. Never colour alone. Every state has a shape or icon, a word, and a colour, in that order of importance. Colour is the third channel. (research g, 4.4.)
  5. Nothing hides without a switch. Contextual elements (badges, stamina, prompts) each have an "always show" position in one option. (The Long Dark split; CDDA #27367 "Please allow this to be an option".)
  6. Consistent navigation everywhere. One menu-navigation context for every list, grid and tab in the game: up/down/left/right, confirm, back, next/prev tab, page, home/end, search, info. A player who can use one screen can use all of them. (P2.)
  7. Controller-first navigation, mouse-first pointing. Every screen is operable with a D-pad and two buttons. Every list and button is also clickable, with correct hit-testing. No virtual cursor. (P6; research f.)
  8. Budget everything. Screens, menu items, options and keybindings all have a number, and the number is held (section 2).
  9. Text scales; layout reflows. Nothing is laid out in fixed character cells in the new layer. 75-200 % UI scale is a first-class state, tested by screenshot. (P4.)
  10. The accessibility tree is the UI tree. Screen-reader narration, controller focus and mouse hit-testing all read the same widget tree; there is no second description of a screen.

3.1 Sidebar replacement (3D mode)

3.2 Map area without the sidebar

Today game::create_or_get_main_ui_adaptor sizes the terrain window as TERMX - (sidebar_left + sidebar_right) (src/game.cpp:4692-4729) and game::draw_panels (game.cpp:4946) draws every panel of the current layout beside it. In 3D mode with the sidebar removed:

  • panel_manager::get_width_left/right() return 0 and draw_panels returns early when RENDERER_3D is active (one predicate, ui::sidebar_hidden()).
  • TERRAIN_WINDOW_WIDTH = TERMX, w_terrain at point_zero; the 3D draw rectangle in src/sdltiles.cpp:1684 already follows w_terrain, so the picture fills the window.
  • Screens that position themselves relative to the sidebar must be re-anchored: look-around info window (game.cpp:10082-10107, uses get_width_left() and LOOKAROUND_POSITION), the offsetX computation at game.cpp:9576, the right-offset block at game.cpp:10531-10539, and pickup/AIM window placement (PICKUP_POSITION). In the new layer these become HUD cards anchored to a screen edge.
  • The pixel minimap window (w_pixel_minimap) is no longer created in 3D mode.
  • Curses and classic 2D are untouched: the predicate is false there.

Risks: anything that reads TERRAIN_WINDOW_WIDTH to compute a sidebar-relative position (grep get_width_left|get_width_right|SIDEBAR_POSITION in game.cpp: 7 sites), the panel manager key (}) must become a no-op with a message in 3D, saved panel layouts must still load for classic mode, and the option toggle at runtime must mark the main ui_adaptor for resize.

4.2 Interaction prompt and secondary verbs

Replaces: examine (e), open/close (o/c), smash (s), pick up (g, single tile), talk (C), board/alight, use furniture, drive, and the examine item menu.

Target selection: in first person the crosshair tile; in orbit the tile in the facing direction, or the tile under the mouse when the pointer is over the scene, or the adjacent tile chosen by holding the interact key and pressing a direction.

[E] Open door                      (primary verb: one press)
[hold E] ⌄ Close | Lock | Examine  (secondary verbs: hold to reveal, release on one)

Rules: one primary verb computed by priority (talk > drive/board > open/close > pick up (single item) > loot (several items, opens Inventory in loot mode) > examine). Up to five secondary verbs in a hold list; more than that is a design error. Smash is a secondary verb on terrain and furniture. The prompt always shows the target's name and, for creatures, their one-word attitude (hostile / neutral / friendly) with an icon.

Gamepad: A primary, hold A for the list, stick to pick, release to run. Keyboard: E and hold E. Mouse: left click = primary, right click = the list as a context menu at the pointer. Hold-vs-toggle: "Confirmation holds" and the global Hold/Toggle apply.

4.3 Action wheel and quick-slot wheel (hotbar)

Two radial menus of eight. Hold to open, direction to pick, release to run. Keyboard: hold Tab (actions), hold Q (quick slots), or press 1-8 directly for quick slots. Mouse: hover a slice. Gamepad: hold LB (actions), hold RB (quick slots); D-pad left/right cycles the hotbar without the wheel.

Action wheel, fixed order: Inventory, Craft, Build, Character, Map, Journal, Wait/rest, Look. These are also the eight screen keys (i, &, *, @, m, j, |, x). The wheel exists so a gamepad reaches every screen in one gesture and so the keys are discoverable.

Quick slots: items (wield, wear, eat, use, read) or actions (fire, reload, throw, sleep, toggle light). Binding: in Inventory, "Assign to slot" on the item card; in the Controls editor for actions. Slots never reorder themselves (BG3 complaint).

4.6 Build (Construct + Zones)

Construct tab mirrors Craft (filters: Can build / Missing one / All; six categories; search; detail card with stages and materials). Differences: choosing a construction enters placement mode over the scene; the menu stays open (Subnautica 2 rule); E places, R rotates where applicable, Esc returns to the list. "Copy this" (C in cursor mode on existing furniture/terrain) selects the matching construction (Satisfactory F+middle-click). The list remembers its tab and selection (BN #8299, #8154).

Zones tab: a list of zones for the current area with type, name, size; verbs: Add (draw a rectangle in cursor mode), Edit, Move, Enable/disable, Delete, Show on map. Replaces the zones manager screen.

Menu count: 6 tabs, 4 verbs (Construct); 6 verbs (Zones).

4.7 Cursor mode (look, target, list)

x (look), f (fire), t (throw) and the "list items/monsters" screens become one mode: a cursor on the scene with a side card. The card describes the tile under the cursor (terrain, furniture, items, creature with attitude, remembered vs seen), and has filter chips "Items" "Creatures" "Terrain" that turn the card into a sorted list of visible things; selecting a row jumps the cursor. Verbs: Fire/Throw (when entered from f/t, with the aim confidence shown as a bar with a word), Travel to, Note, Copy construction, Peek. The narrator reads the card on every cursor move (section 7.3).

Menu count: 3 chips, 6 verbs.

4.8 Vehicle

Opened by interacting with a vehicle part. Replaces veh_interact (3270 lines, 24 bound actions) with a screen of three areas: a top-down part grid (reuses vehicle_preview), a part card (state, fuel, controls), and verbs: Install, Repair, Remove, Refill/Siphon, Rename, Change tyre, Assign crew/animal; "Examine contents" opens Inventory in loot mode. Driving controls (lights, cruise, horn, engine) live on the HUD vehicle cluster and the action wheel while seated, not in this screen.

Menu count: 8 verbs. This is the hardest screen and is last in the plan.

5. Input model

5.1 Actions and contexts

The unit stays the action id (data/raw/keybindings/*.json). Contexts become twelve (section 2.4) and nest: global < play | menu | cursor | text; inventory, craft, build, map, vehicle, dialogue extend menu; debug extends global. A screen registers only its own verbs; navigation comes from menu. This fixes "rebinding movement breaks menus" (CDDA #45927): menus do not use movement actions.

The menu context: up, down, left, right, confirm, back, next tab, prev tab, page up, page down, home, end, search, info, help, mark, mark all, sort, secondary (context menu). 18 actions, bound once.

5.2 Devices

  • Keyboard: key + modifiers (Ctrl, Shift, Alt) captured as a unit. Today modifiers are not capturable in the editor (research m, A). Movement presets set the eight directions, wait, and stairs.
  • Mouse: left, right, middle, wheel, with modifiers; movement by click-to-travel on the scene (existing auto-travel); right-click context menu = the hold-list of the prompt; middle drag stays the camera (shipped). Every list row and button is hit-tested.
  • Gamepad: replace SDL_Joystick (hat-only, buttons sent as keyboard events, no sticks: src/sdltiles.cpp:1871-1935, 3499-3503) with SDL_Gamepad: hot-plug, named buttons, sticks with dead zones, rumble, SDL_GetGamepadButtonLabel for glyphs (available in the system SDL 3.4.18 header). 5.4 Hold vs toggle

Holdable actions: run, crouch, aim mode, action wheel, quick-slot wheel, interact hold-list, camera glance, map pan. Each has a per-action setting (Hold / Toggle / Default) in the Controls editor; the global default is in Accessibility. Confirmation holds (long-press to confirm destructive verbs) can be "press twice" instead.

6. Options architecture: in-game versus file

Rule for placing an option: it stays in-game if (a) a player changes it in a normal session (language, volume, scale, HUD mode, controls, accessibility), or (b) it is an accessibility need. Everything else is in the advanced file. Options that are "tuning" of a feature the player already turned on (particle density, fade times, minimap pixel ratio, FOV tween) are file-only. Debug and developer options are file-only. Duplicate signals are merged (five unit options to one; nine minimap options to one toggle; three autosave options to one).

The advanced file is specified in section 9.

7. Accessibility

All items are in the Accessibility tab (11 options) plus the Controls editor. Presets set several of them at once and are documented as such; a preset is never the only way to reach an option.

7.1 Remapping

Every action, every device, in one editor (4.13). Modifiers and middle mouse capturable. Conflicts shown and fixable inline. Presets include Left-handed (mirrored movement and verbs) and One-handed (7.9). Mods that add actions appear in the same list. Bindings are stored per device so a keyboard rebind never touches the gamepad.

7.2 Colour vision and non-colour redundancy

Rules first: every state carries (1) an icon shape or glyph, (2) a word, (3) a colour. Lists that use colour for rarity/condition also show the word. Deltas show sign and arrow. Hostile vs neutral vs friendly creatures show an icon on the prompt and on edge arrows.

Palettes: UI semantic tokens use the Okabe-Ito set, designed to stay distinct under deutan, protan and tritan vision (hex from a secondary source; verify against jfly.uni-koeln.de before shipping; see research g):

"High contrast" is a fourth mode: UI on black with the token set at full saturation, and in the 3D scene hostiles, items and interactables tinted with tokens while the rest desaturates (TLOU2 style).

Contrast: text ≥ 4.5:1 against its background, UI components ≥ 3:1 (WCAG 2.2 SC 1.4.3 and 1.4.11), checked by a Catch2 test over the theme tokens.

7.3 Screen reader and self-voicing

Architecture (detail in 04_architecture.md §5): the widget tree carries, per node, a role, a name, a value, a state and an optional description. A narrator walks it:

  • Screen open: speak title, then a one-line hint ("Inventory. 3 sections. Tab to switch.").
  • Focus change: speak "name, value, state, position" ("Survivor jacket, worn on torso, 1.8 kilograms, 7 of 24"). Verbosity Low drops position and state.
  • Value change on the focused control: speak the new value.
  • HUD events (narration = Menus and log): new log lines, badge appear/disappear ("Cold"), "Entering: place", interrupt popups. Combat text is not spoken separately; the log line is.
  • Cursor mode: speak the tile card on every move ("Door, closed. Zombie, hostile, 3 tiles north-east."). This is the blind-navigation path for the map.
  • Keys: F4 speaks the status report (already text); Ctrl+R repeats the last utterance; Ctrl+Up/Down reads the previous/next line of the current card without moving focus.
  • Queue rules: focus and screen changes interrupt; log lines queue; a volume and rate slider.

Speech backends (research h): Windows: NVDA controller client (LGPL-2.1, dynamically loaded) when NVDA is running, else SAPI 5 via COM; Tolk is not used (its README says it is not being developed). macOS: AVSpeechSynthesizer through a small Objective-C++ file. Linux: libspeechd loaded with dlopen (present on this machine, 0.12.1; Flatpak/SteamOS access to the daemon is unverified). SDL3 has no speech API. This is self-voicing; it works with or without a screen reader. A second phase exposes the same tree through AccessKit's C API (Apache-2.0 or MIT; accesskit-c repository exists) so JAWS/NVDA/VoiceOver/Orca can navigate the UI natively; this is deferred until the self-voiced UI is complete, because the accessibility tree it needs is the same tree.

Trade-off stated plainly: self-voicing gives blind players a playable game soonest and does not depend on the still-experimental AccessKit adapters, at the cost of a second speech stream when a screen reader is also running (mitigated: when NVDA/JAWS/Orca is detected the narrator routes through it instead of SAPI/speechd).

7.4 Text and UI scale

One slider, 75-200 % in 5 % steps, applied live (no restart) to every new-layer screen and the HUD. Floor is computed so the smallest glyph is ≥ 9 px at 1280x800 (Steam Deck rule), target 12 px. The map/tile zoom stays a separate in-play key. Fonts: default UI font plus "Readable font" (Atkinson Hyperlegible; dyslexia-specific fonts are not shipped, the evidence for them is weak; research i §8), CJK/emoji fallbacks via TTF_AddFallbackFont. Every screen reflows: cards wrap, lists scroll, nothing truncates (P4). Screenshot tests at 100 % and 200 %.

7.5 Reduced motion and flashing

One switch: camera easing off, HUD fades replaced by instant show/hide, hit-direction pulse replaced by a static chevron for one turn, lightning flash removed (sky brightens without the frame flash), screen shake (if any) off, precipitation particle count halved. The game's baseline must already pass WCAG 2.3.1 (≤ 3 flashes per second); the lightning flash and the hit glow are the two effects to measure (research g §6).

7.6 Audio cues as text

"Sound cues as text" shows a subtitle line for every heard sound in the message ticker with direction and distance words ("You hear glass breaking, east, close"), speaks it when the narrator is on, and keeps the in-world sound markers (shipped). NPC speech is already text. Music and ambient cues carry no information in BN, so nothing else is needed.

7.7 Cognitive load

HUD Minimal, Guided hints, the Reference's "explain this screen" (F2), consistent navigation, no timed popups, one verb per interaction, lessons re-readable in the Journal. "Confirmations: All" adds a confirm step to every irreversible verb.

7.8 Hold vs toggle

Section 5.4. Also: no action requires two simultaneous inputs; the LT gamepad modifier and keyboard modifiers can be set to "sticky" (press, then press the key) in the Controls tab (this is one row: Sticky modifiers Off/On, counted within the Controls editor, not the 39).

7.9 One-handed and switch-friendly play

  • One-handed presets (left and right): movement on one hand's cluster, verbs on the same cluster, radials for everything else; nothing on the far side of the keyboard.
  • Mouse-only play is possible: click-to-travel, right-click verb list, hotbar and wheels clickable, every screen clickable, scroll wheel for lists. BN is turn-based, so speed is not an issue.
  • Single-switch scanning is not built in (it is a large, separate feature); instead the command palette guarantees every action is reachable by typing, which works with external switch-to-keyboard tools, and the Reference lists every action. Stated as a limitation.

8. Theming

Two shipped themes: Dark (default) and High contrast; the Modern menu border option is subsumed. Theme = a JSON token file (colours, spacing scale, corner radius, border width, font family) in data/raw/ui/themes/; the classic look is a third theme file (plain borders, no padding) so "make it look like before" is a theme choice, not an option. Colour vision modes layer over any theme.

9. The advanced config file

  • File: config/advanced.json (next to the existing config/options.json).
  • Format: one flat JSON object. Keys are option ids in lower case; values are the typed value. A "//key" entry before each option carries its description and allowed values, so the file is self-documenting without a comment syntax: 
{
  "//message_ttl": "Turns a message stays in the ticker. integer 1-1000. default 10",
  "message_ttl": 10,
  "//r3d_fp_tween_ms": "First-person step easing, milliseconds. 0 disables. default 90",
  "r3d_fp_tween_ms": 90
}
  • Generation: on first run the game writes the file with every advanced option at its default and its description. cataclysm-bn-tiles --dump-advanced-options prints the same list as Markdown for docs/en/user/advanced_options.md, so the doc is generated, not maintained.
  • Reload: read at launch, when the Settings screen closes, and when returning to the main menu. Options marked "restart" in their description apply at the next launch; the Settings screen shows a one-line "advanced.json changed; N settings need a restart" notice.
  • Validation: unknown key → warning in the log, ignored; wrong type or out of range → default used, warning in the log; the file is never rewritten by the game after creation except by an explicit "Reset advanced settings" row under Settings > Game (that row is the 40th item and is a verb, not an option).
  • Migration: existing options.json values for moved options are copied into advanced.json once, then ignored.

(The terminal build itself is retired; these screens draw through the in-process cell canvas, cursesport.cpp, until they are ported or dropped.)

11. Feature cuts (last resort)

Each lists the alternatives rejected before proposing the cut. None is required for the design; they reduce the long tail of legacy screens.

  1. Defense mode (and its Caravan shop). Two bespoke curses screens (DEFENSE_SETUP, CARAVAN contexts) for a game mode outside the survival loop. Rejected alternatives: port to the new layer (a full screen's cost for a mode with no evidence of use); keep on the legacy path (cheap, but it keeps the old uilist stack alive and inconsistent with principle 6). Recommendation: keep on the legacy path, mark "Legacy" in the mode list, and cut only when the legacy stack is retired.
  2. Item minigames (Sokoban, Minesweeper, Lights on). Three keybinding contexts and three screens for console items. Rejected alternatives: port (cost for no gain); replace the items' use with a morale effect only (a rule change for a trivial feature). Recommendation: same as 1.
  3. "Examine also picks up" (BN #9805). Not a feature cut: the interaction prompt makes examine and pick up distinct verbs on the same target, which answers the complaint without changing what the player can do.

No other game-rule cut is proposed. The brief's permission to cut was not needed for the design: the complexity players complain about is in the screens, not in the rules.
